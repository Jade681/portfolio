# 求职申请与面试 AI 工作流

作者：张馨洁（Xinjie Zhang）
配套说明页：<https://jade681.github.io/my-flask-website/projects/job-workflow.html>

把求职里最费神、最容易出错的一整条链路——**看懂岗位 → 匹配自己的经历 → 判断值不值得申请 → 准备自我介绍和定向简历 → 预测面试题 → 面试后复盘并归档**——做成一套可以对不同岗位反复运行的方法。

它由两个相互衔接、又能各自独立使用的 Skill 组成：

| Skill | 负责什么 | 能不能单独用 |
|---|---|---|
| **job-application-copilot（求职副驾）** | 整理岗位、整理个人证据、做判断、产出定向简历和面试准备文档 | 能 |
| **job-interviewer（面试官视角）** | 独立建岗位评分卡、设计笔试或面试、逐题追问、给候选人反馈、帮面试官复盘 | 能（也可用于社团招新、项目选人） |

关系是：**求职副驾在进入真实笔试 / 面试评估阶段时，调用面试官视角。** 面试官视角不依赖求职副驾。

---

## 一条核心原则：每句话都要有出处

所有产出都遵循同一个取信顺序，越靠前越可信：

1. 用户本人确认过的说法和更正
2. 可核对的原始材料：母简历、项目文件、作品集、代码仓库、已公开作品
3. 保留了来源和不确定性的证据笔记
4. AI 推断——必须标成推断，永远不能被当作事实

母简历只作**事实源**，不被改写；每份针对具体岗位的定向简历都单独成文件。

## 求职副驾：八个步骤

给一份真实的 JD（岗位描述），依次跑完下面八步，最后合成一份可追溯的求职准备文档。

### 第一步　看懂岗位

把 JD 拆成「显性事实」和「需要推断的部分」，先用大白话回答四个问题：

- 这个岗位主要解决什么问题？
- 最重要的三项能力是什么？
- 哪些条件必须满足？
- 招聘方在面试里可能考察什么？

每条结论都要**贴一小段 JD 原文**，再写出从原文到结论的推理链；没有原文支撑的，标成「推断」或「未知」，不能写成事实。要求按重要性排序（在 JD 里重复出现、放在岗位专属段落、和核心产出相关、用了「必须 / required」这类词，都是有效信号）。

如果 JD 有城市、坐班、到岗时间、每周出勤、时长这类要求，先做一次「现实条件核对」，只问会改变结论的问题（能否在该城市工作、最早到岗时间、可做多久、每周几天），不把当前所在城市直接抄进定向简历。

### 第二步　匹配我的经历

在母简历和个人材料里找**具体证据**。对每条经历记录：来源、当时的情境或问题、我自己的行动和判断、可观察的结果或产出、验证来源、置信度和缺失细节、以及 AI / 队友 / 我各自的贡献。

把每条岗位要求对应到「强 / 部分 / 弱 / 缺失」四档。不把性格标签（「有创意」「负责」）当证据，除非配了具体行动例子。

### 第三步　判断优势与缺口

改简历之前，先把能力分成三类：

1. 有真实经历能证明的
2. 自己以为具备、但证据还不充分的
3. 目前明显的缺口

每个重要风险都要配三条应对：**投递前怎么补强、面试前准备什么证据、暂时补不齐时如何诚实表达**。行动力度要和申请时间线匹配，不为一个小缺口开一个大项目。

### 第四步　判断是否值得申请

做**双向匹配**，给建议但不替用户做决定：

- 我相对这个岗位的最大优势
- 我相对这个岗位的最大能力或条件风险
- 这个岗位对我的最大价值
- 这个岗位对我的最大风险或代价
- 需要向招聘方确认的问题
- 投递前最需要准备的事

不把结论压缩成一个「匹配分数」。学习价值、工作内容、带教、通勤、不确定性、机会成本都要纳入考量。

### 第五步　准备自我介绍

用 **FAB** 结构，按场景和听众挑 2—3 个有证据支撑的点：

- **Feature（特征）**：想呈现的身份、经历、技能或职责
- **Advantage（优势）**：它对这个具体岗位 / 场合为什么重要
- **Benefit（对听众的价值）**：它能给对方、团队、面试官带来什么

默认产出 1 分钟、2 分钟、3 分钟三个版本，并标出每句话对应 F / A / B，再说明各版本侧重什么、长版本比短版本多讲了什么、什么时候用哪个。除非面试官明确要求，一般不超过 3 分钟。

### 第六步　生成定向简历

从母简历里**已核实的事实**中挑选、重排，生成一份针对这个岗位的简历。每条 bullet：

- 先写和岗位最相关的问题 / 行动 / 职责
- 写清我的决策和行动
- 有支撑才写结果
- 用具体的范围、产出、反馈，而不是夸大的形容词
- 保留「AI 辅助 / 团队完成 / 进行中 / 尚未验证」这些边界
- 绝不编造指标、头衔、日期、技术或归属

交付前，把每条新说法和证据表逐条比对，标出没有支撑的措辞并改掉。附一份**改动说明**：留了什么、删了什么、怎么重排、为什么。有公开链接的作品，用简短可点击的链接（「Demo」「GitHub」或作品名），并在交付前核对链接有效。

### 第七步　预测面试题

从排过序的要求和证据弱点里预测**十个**高概率问题，不套通用题库。每题标：考察什么、我可以用哪段已核实的经历、可能的追问、目前的准备缺口。没有经历能对上的，直接标成缺口并给准备动作，不硬凑故事。

面试回答用 **STAR + 难点**（情境、任务、行动、结果，再加上当时真实的障碍 / 约束 / 取舍）。同时准备：对公司和业务的理解、语速控制、和面试官建立连接、应对突发追问、「怎样能更完美」这类追问、可持续的求职动机、以及对反馈的响应。

### 第八步　练习与复盘

两种模式，不混用：

- **教练式逐题演练**：一次问一题，答完后评估具体性、可信度、相关性、反思和抗追问能力，给出更强、但仍真实的版本，再进入下一题。保留原答案和修改版。
- **真实模拟**：交给 job-interviewer 那一层来当面试官。过程中不指导、不给标准答案、不报中间分数。笔试一次性发全、批量作答后再评；面试一次一题。结束后给一份统一评估。

真实投递 / 笔试 / 面试之后，做**结构化复盘**：记录公司、岗位、日期、阶段，真实题目和追问，哪个回答建立或削弱了信任，哪些事实答不上来，结果和招聘方反馈。更新分成三处——**申请记录**（这次发生了什么）、**个人证据库**（只加新确认的事实）、**方法本身**（只有真正能改进以后决策的经验才写回）。最后把整个周期归档进知识库。

## 面试官视角：完整闭环

```text
岗位与实际任务
  → 显性要求、任务反推、不确定假设
  → 岗位评分卡
  → 岗位统一题（所有候选人可比） + 针对候选人材料的定制题
  → 真实市场与业务场景校准
  → 笔试 或 逐题面试
  → 初步证据整理
  → 按岗位与候选人表现生成反馈
  → 最终证据评估与决策记录
  → 面试官采访式反思
  → 候选人案例 / 岗位画像 / 方法本身分层更新
```

**追问深度（三层法）** —— 每一层是一个目的，不是三道越来越难的题：

1. **第一层 · 给机会**：问一个相对开放的问题，让候选人自己选一段相关经历，别因为第一次回答模糊就判定能力缺失。
2. **第二层 · 要具体**：如果第一层没拿到可用证据，把问题问得更具体（澄清情境、本人角色、顺序、决策、约束、结果），继续帮候选人展示同一种能力，不是设陷阱。
3. **第三层 · 换条路**：只有前两层还没显现目标特质时，换场景、换方法、换经历，再给一次独立的机会。不是「更难的施压」。

之后记录的是「有证据 / 证据混合 / 仍未评估」，而不是没有依据的负面结论。

**候选人反馈** —— 不是固定模板，也不在面试过程中边问边指导。评估明确结束后，按「**观察到的证据 → 对这个岗位的影响 → 可执行的下一步**」给出：优先给一项有证据的优势和一到两项最重要的改进，不为了显得平衡而虚构表扬，也不把「没问到」说成「候选人不会」。结果没确认前，反馈和录用 / 晋级结论分开。

## 怎么用

这两份 `SKILL.md` 是给能读取技能文件的 AI 助手用的（如 Claude Code / Codex 等的 Skill 机制）。把 `skills/` 下的目录放进你的技能目录，在对话里提供一份真实 JD 和你的个人材料，让它运行 `job-application-copilot`；进入真实笔试 / 面试阶段时它会调用 `job-interviewer`。也可以只把 `job-interviewer` 单独用于招新或选人。

即使不接入 AI，这套文档本身也可以当作一份**求职准备清单**逐步照做。

## 隐私

仓库里只有通用方法，不含任何个人履历、面试记录、组员信息或未公开材料。运行时产生的个人证据库、申请记录和面试记录都保存在本地 / 私人知识库，不进入本仓库。
